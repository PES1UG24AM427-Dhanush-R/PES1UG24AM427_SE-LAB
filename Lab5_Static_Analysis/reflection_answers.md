# Reflection — Lab 5: Static Code Analysis

## Question 1: What is static code analysis, and how does it differ from dynamic testing?

Static code analysis examines source code without executing it, identifying potential bugs, style violations, and security vulnerabilities purely by reading the text and structure of the program. Dynamic testing, by contrast, runs the program and observes its behaviour at runtime — it can only catch problems that surface during a particular execution path with a particular set of inputs. In this lab, Pylint caught the mutable default argument `logs=[]` on line 10 without ever running the function; a dynamic test would only reveal the bug if the test called `register_asset()` multiple times without passing an explicit list, which is easy to miss. Similarly, Bandit flagged the `tempfile.mktemp()` TOCTOU race condition statically — a race condition is almost impossible to reproduce reliably in a dynamic test because it depends on timing between processes. Static analysis therefore provides broad, reproducible coverage of an entire codebase in seconds, while dynamic testing validates actual runtime behaviour for specific scenarios.

## Question 2: Which tool found the most actionable issues, and what does that tell you about code quality?

Pylint found the most actionable issues, raising ten distinct warning and convention codes (W0611, C0114, eight C0116 instances, W0102, W0702, C0206, C0103, W0603, W1514, R1732) and driving the initial score of 5.64/10 up to a perfect 10.00/10 after fixes. This breadth tells us that the code had accumulated a significant amount of technical debt in the areas Pylint is designed to measure: missing documentation, poor naming, unsafe patterns, and style inconsistencies. The sheer number of missing docstrings (one per function, plus the module) shows that documentation was treated as optional rather than integral, which makes maintenance harder. The mutable default argument and bare `except` findings indicate logic-level problems, not just style, meaning the code could behave unexpectedly in production. A low Pylint score is therefore a reliable early warning that a codebase needs more than cosmetic cleanup.

## Question 3: How did fixing the issues improve the program?

The most important improvements were correctness and security fixes rather than style changes. Replacing `logs=[]` with the `None`-guard pattern removed a subtle state-sharing bug where repeated calls to `register_asset()` without an explicit list would accumulate entries from every previous call, corrupting the count. Replacing `tempfile.mktemp()` with `tempfile.NamedTemporaryFile` used as a context manager eliminated the TOCTOU race condition and ensured the file handle is always properly closed. Replacing `assert assets` with an explicit `RuntimeError` means the guard works correctly even when the interpreter's optimisation flag is set. Beyond correctness, adding docstrings to every function makes the code self-documenting, and fixing the bare `except` to `except KeyError` ensures that only the expected error is silently handled, allowing unexpected exceptions to propagate and be noticed. Together these changes moved the file from a working-but-fragile script to code that is readable, defensively correct, and free of known security warnings.

## Question 4: What are the limitations of static analysis tools?

Static analysis tools cannot observe runtime state, so they miss bugs that only appear under specific inputs or concurrency conditions — for example, none of the three tools noticed that `change_interval(-30)` would set a nonsensical negative service interval, because the tools do not know what values are semantically valid. Tools also produce false positives: Pylint's C0103 name-length rule flagged legitimate short names in contexts where brevity is perfectly readable, requiring judgment about which findings to act on. Bandit flags patterns conservatively (it flagged `assert` as low-severity), meaning developers must distinguish genuine security risks from informational warnings or risk alert fatigue. Finally, static tools do not replace integration tests or code review: they confirm that the code follows known patterns of correctness, but they cannot verify that the overall program logic is right — for instance, whether the `due_for_inspection` threshold logic is actually correct for the business domain requires a human or a test with real dates.
